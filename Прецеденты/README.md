# Прецеденты: как с ними работать

Здесь лежат прецеденты ИС поликлиники. Каждый в команде ведет один прецедент в своей папке. Общая картина в [Диаграмме прецедентов](Диаграмма%20прецедентов.md): там диаграммы, актеры и таблица, где для каждого прецедента расписаны границы (колонка «Что входит»).

## Что должно лежать в папке

1. **`<Название прецедента>.md`**: подробное описание прецедента. Образец: [Запись на прием](Запись%20на%20прием/Запись%20на%20прием.md). Формат тот же, что у «Оформления продажи» из примера [penamarth/pos](https://gitlab.com/penamarth/pos).
2. **`Диаграмма последовательности <Название прецедента>.md`**: основной успешный сценарий в виде диаграммы последовательности. Обязательна по заданию.
3. По желанию **`Описание операции <имяОперации>.md`**: контракт главной системной операции, вроде «Описания операции enterItem» в примере.

## Разделы описания прецедента

Разделы идут в том же порядке, что и в образце:

1. Рамки. Уровень. Основной исполнитель.
2. Заинтересованные лица и их требования.
3. Предусловия. Результаты (Постусловия).
4. Основной успешный сценарий: нумерованные шаги "кто что делает". Действия пользователя на экране пишем одной строкой ("пациент выбирает специальность и день"), без кнопок и полей. В шаге, где работает ПолиКлик, в скобках ставим имя системной операции из Диаграммы классов, например "(`bookAppointment`)". Цепочки вызовов классов в описание не пишем, они на диаграмме последовательности.
5. Расширения (или альтернативные потоки).
6. Специальные требования.
7. Список технологий и типов данных.
8. Частота использования.
9. Открытые вопросы.

### Нумерация расширений
- `*а`, `*б`: расширения, которые могут случиться на любом шаге. Их пишем первыми.
- `3а`, `3б`: альтернативы шагу 3 основного сценария. Остальные расширения идут за `*`-расширениями по возрастанию номера шага.
- Вложенные альтернативы считаются от шагов своего расширения: `2а` внутри `3а` значит «альтернатива шагу 2 расширения 3а».
- «Список технологий» повторяет порядок расширений.

## Что уже зафиксировано

Все это уже есть в общих файлах. Берите оттуда, заново не придумывайте:

- **Название системы.** ПолиКлик (см. [Видение](../Видение.md)). В «Рамках» и заголовках пишем ИС «ПолиКлик», в шагах сценария просто ПолиКлик: «ПолиКлик показывает...», а не «Система показывает...». Склоняем как обычное слово: «в ПолиКлике», «пользователи ПолиКлика».
- **Актеры и внешние системы.** Только те, что нарисованы на [Диаграмме прецедентов](Диаграмма%20прецедентов.md), и под теми же именами: «Медрегистратор», «Система ОМС (ТФОМС)», «Сервис уведомлений».
- **Границы прецедента** смотрите в колонке «Что входит» таблицы прецедентов. Сценарий залез в чужой прецедент? Сошлитесь на него, описывать второй раз не надо.
- **Включаемые прецеденты** есть на рис. 2 диаграммы. Когда в сценарии идентифицируют пациента, так и пишите в шаге: «(включается прецедент «Идентификация пациента»)».
- **Термины** берем из [Словаря терминов](../Словарь%20терминов.md), **правила** из [Бизнес-правил](../Бизнес-правила.md). На правило ссылайтесь по номеру: «(ПРАВ7)».

### Если нужно что-то новое
- **Новый термин** добавьте строкой в Словарь терминов, на свое место по алфавиту.
- **Новое правило** пишите в конец Бизнес-правил под следующим свободным номером. Смысл чужих правил без обсуждения с командой не меняйте.
- С **новым актером или внешней системой** сначала идите к команде: придется менять диаграмму прецедентов, Видение и контекстную диаграмму.

Общие файлы правьте отдельным коммитом и предупреждайте команду в чате, иначе могут быть конфликты.

## Диаграммы

- Диаграмма живет прямо в md-файле: блок ` ```plantuml `, внутри `@startuml` … `@enduml`.
- Классы, атрибуты и методы называем по-английски (`Patient`, `bookAppointment()`), все остальное пишем по-русски.
- Копию каждой диаграммы картинкой кладите в `img/` в корне. GitHub блоки plantuml не показывает.

Классы и методы берите из [Диаграммы классов](../Диаграмма%20классов.md): следующие прецеденты строятся по ней, так диаграммы последовательности из разных прецедентов стыкуются. Если нужен новый класс или метод, сначала добавьте его в Диаграмму классов, а класс еще и в эту таблицу:

| Понятие | Класс |
| --- | --- |
| Поликлиника (корневой объект и единственный контроллер: в нем все системные операции, при запуске создает хранилища) | `Clinic` |
| Пациент | `Patient` |
| Полис ОМС | `OmsPolicy` |
| Прикрепление | `Attachment` |
| Участок | `District` |
| Льгота | `Benefit` |
| Медицинская карта (ЭМК) | отдельного класса нет. Это записи `MedicalRecord`, которые хранятся у `Patient` |
| Запись в медкарте | `MedicalRecord` |
| Диагноз (МКБ-10) | `Diagnosis` |
| Справочник МКБ-10 | `Icd10Catalog` |
| Сотрудник (общий предок всех сотрудников) | `Employee` |
| Врач (только данные: ФИО и специальность, слотов и записей у него нет) | `Doctor` |
| Заведующий отделением (тоже врач) | `HeadOfDepartment` |
| Медрегистратор | `Registrar` |
| Системный администратор | `SystemAdministrator` |
| Учетная запись сотрудника | `UserAccount` |
| Специальность | `Specialty` |
| Отделение | `Department` |
| Кабинет | `Cabinet` |
| Рабочая смена (часы работы врача в кабинете, из нее нарезаются слоты) | `WorkShift` |
| Слот | `TimeSlot` |
| Запись на прием | `Appointment` |
| Лист ожидания (заявка) | `WaitingListEntry` |
| Прием (визит) | `Visit` |
| Направление | `Referral` |
| Табло электронной очереди (одно на группу из 3–4 кабинетов) | `QueueBoard` |
| Хранилище пациентов | `PatientStorage` |
| Хранилище (пул) врачей | `DoctorStorage` |
| Хранилище расписания: смены и слоты | `SlotStorage` |
| Хранилище сотрудников | `EmployeeStorage` |
| Сервис уведомлений (интерфейс внешней системы) | `NotificationService` |
| ЕГИСЗ (интерфейс внешней системы) | `EgiszService` |
| ТФОМС (интерфейс внешней системы) | `TfomsService` |
| ЕСИА (интерфейс внешней системы) | `EsiaService` |
| Вывод вызова на экран табло (интерфейс) | `BoardDisplay` |

Расписание хранится в `SlotStorage`: смены врача (`WorkShift`) и нарезанные из них слоты (`TimeSlot`). Свободные слоты, записи врача на день и запись по номеру ищутся там же, а не через `Doctor`. Записи медкарты хранятся у пациента: `Patient` -> `MedicalRecord`. На диаграмме последовательности актер вызывает системную операцию прямо у `:Clinic`, экранов (UI) там нет. Все системные операции перечислены в Диаграмме классов, вид 7. Статусы и типы заданы перечислениями (`AppointmentStatus`, `VisitType`, `RecordStatus`, `ReferralKind`, `DetachReason`, `Role`), их значения есть в Диаграмме классов.

## Как мы работаем
- В свой коммит кладите только файлы из своей папки. Общие файлы идут отдельным коммитом (см. выше).
