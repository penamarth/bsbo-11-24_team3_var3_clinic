# Прецеденты: как с ними работать

Здесь лежат прецеденты ИС «ПолиКлик». Каждый в команде ведет один прецедент в своей папке. Общая картина в [Диаграмме прецедентов](Диаграмма%20прецедентов.md): там диаграммы, актеры и таблица, где для каждого прецедента расписаны границы (колонка «Что входит»).

## Кто за что отвечает

| Прецедент | Папка | Ответственный |
| --- | --- | --- |
| Запись на прием | [Запись на прием](Запись%20на%20прием/) | Niron3206 |
| Прием пациента и ведение медкарты | [Прием пациента и ведение медкарты](Прием%20пациента%20и%20ведение%20медкарты/) | deuf00 |
| Электронная очередь | [Электронная очередь](Электронная%20очередь/) | xlllaMaH |
| Постановка и снятие с учета | [Постановка и снятие с учета](Постановка%20и%20снятие%20с%20учета/) | |
| Администрирование | [Администрирование](Администрирование/) | asbaryshev |

Впишите себя в таблицу, когда возьмете прецедент. `.gitkeep` лежит в папке только затем, чтобы git не потерял ее, пока она пустая. Положите свой файл, и `.gitkeep` можно удалить.

## Что должно лежать в папке

1. **`<Название прецедента>.md`**: описание цели пользователя, поведения ПолиКлика, результатов и альтернативных ситуаций. Образец: [Запись на прием](Запись%20на%20прием/Запись%20на%20прием.md). Формат тот же, что у «Оформления продажи» из примера [penamarth/pos](https://gitlab.com/penamarth/pos).
2. **`Диаграмма последовательности <Название прецедента>.md`**: взаимодействия объектов в реализованной части сценария. Обязательна по заданию.
3. По желанию **`Описание операции <имяОперации>.md`**: контракт конкретной операции с ее параметрами, предусловиями и изменениями объектов. Образец в примере: «Описание операции enterItem».

## Требования и реализация

Описание прецедента задает поведение ПолиКлика с точки зрения пользователей. В нем сохраняем согласованные требования, даже если часть функций еще не написана. Имена классов и методов, исключения, коллекции и ограничения консольного прототипа в описание не включаем.

Диаграмму классов, диаграммы последовательности и контракты сверяем с текущим кодом. В диаграмме последовательности показываем реализованную часть сценария; она может охватывать меньше, чем полное описание прецедента. Возможности и ограничения прототипа описаны в [README кода](../src/README.md).

После согласования изменений пишем код в `src/`, запускаем демонстрацию и проверки, затем обновляем связанные диаграммы и контракты. Описание прецедента меняем, когда меняются требования или поведение для пользователя.

## Разделы описания прецедента

Разделы идут в том же порядке, что и в образце:

1. Рамки. Уровень. Основной исполнитель.
2. Заинтересованные лица и их требования.
3. Предусловия. Результаты (Постусловия).
4. Основной успешный сценарий: нумерованные шаги "кто что делает". Действия на экране описываем одной строкой, без перечисления кнопок и полей. В шагах ПолиКлика указываем результат для пользователя; вызовы методов показываем на диаграмме последовательности.
5. Расширения (или альтернативные потоки).
6. Специальные требования.
7. Список технологий и типов данных.
8. Частота использования.
9. Открытые вопросы.

### Нумерация расширений
- `*а`, `*б`: расширения, которые могут случиться на любом шаге. Их пишем первыми.
- `3а`, `3б`: альтернативы шагу 3 основного сценария. Остальные расширения идут за `*`-расширениями по возрастанию номера шага.
- Вложенные альтернативы считаются от шагов своего расширения: `2а` внутри `3а` значит «альтернатива шагу 2 расширения 3а».
- «Список технологий» повторяет порядок расширений.

## Что уже зафиксировано

Все это уже есть в общих файлах. Берите оттуда, заново не придумывайте:

- **Название системы.** ПолиКлик (см. [Видение](../Видение.md)). В «Рамках» и заголовках пишем ИС «ПолиКлик», в шагах сценария просто ПолиКлик: «ПолиКлик показывает...», а не «Система показывает...». Склоняем как обычное слово: «в ПолиКлике», «пользователи ПолиКлика».
- **Актеры и внешние системы.** Только те, что нарисованы на [Диаграмме прецедентов](Диаграмма%20прецедентов.md), и под теми же именами: «Медрегистратор», «Система ОМС (ТФОМС)», «Сервис уведомлений».
- **Границы прецедента** смотрите в колонке «Что входит» таблицы прецедентов. Сценарий залез в чужой прецедент? Сошлитесь на него, описывать второй раз не надо.
- **Включаемые прецеденты** есть на рис. 2 диаграммы. Когда в сценарии идентифицируют пациента, так и пишите в шаге: «(включается прецедент «Идентификация пациента»)».
- **Термины** берем из [Словаря терминов](../Словарь%20терминов.md), **правила** из [Бизнес-правил](../Бизнес-правила.md). На правило ссылайтесь по номеру: «(ПРАВ7)».

### Если нужно что-то новое
- **Новый термин** добавьте строкой в Словарь терминов, на свое место по алфавиту.
- **Новое правило** пишите в конец Бизнес-правил под следующим свободным номером. Смысл чужих правил без обсуждения с командой не меняйте.
- С **новым актером или внешней системой** сначала идите к команде: придется менять диаграмму прецедентов, Видение и контекстную диаграмму.

Общие файлы правьте отдельным коммитом и предупреждайте команду в чате, иначе могут быть конфликты.

## Диаграммы

- Диаграмма живет в md-файле: блок ` ```plantuml `, внутри `@startuml <имя-латиницей>` … `@enduml`. Имя задает название PNG.
- Классы, атрибуты и методы называем по-английски (`Patient`, `BookAppointment()`), все остальное пишем по-русски.
- Копию каждой диаграммы картинкой кладите в `img/` в корне и добавляйте ссылку на нее рядом с блоком. Перед сдачей отрендерите и просмотрите картинку: GitHub блоки plantuml не показывает.

Имена классов и методов сверяйте с [кодом](../src/PoliClick/) и [Диаграммой классов](../Диаграмма%20классов.md). В реализации используем три хранилища с доски преподавателя: `PatientStorage`, `DoctorStorage`, `SlotStorage`. Их создает `Clinic`.

### Классы текущего прототипа

| Понятие | Класс |
| --- | --- |
| Поликлиника: создает хранилища, оформляет записи, начинает приемы и обновляет очередь | `Clinic` |
| Хранилище пациентов | `PatientStorage` |
| Хранилище врачей | `DoctorStorage` |
| Хранилище расписания: создание и поиск слотов | `SlotStorage` |
| Пациент и его история записей | `Patient` |
| Врач: ФИО, специальность и длительность слота | `Doctor` |
| Интервал приема врача в определенном кабинете | `TimeSlot` |
| Запись на прием и результаты проведенного приема | `Appointment` |
| Табло для группы кабинетов и текущие вызовы | `QueueBoard` |

Расписание состоит из `TimeSlot`. `SlotStorage` ищет доступные дни и время, `PatientStorage` находит пациента, а `DoctorStorage` возвращает врачей и специальности. Созданные записи хранятся у пациента и в `Clinic`. При начале приема `Clinic` возвращает существующий `Appointment`; врач продолжает заполнять этот объект локально.

Одно `QueueBoard` обслуживает группу кабинетов. Все табло поликлиники доступны через `Clinic.QueueBoards`; кабинет относится только к одному табло. Программа вызывает `Clinic.UpdateQueue()` по таймеру: метод выбирает записи по времени слотов с учетом занятости врача, пациента и кабинета. Время вызова сохраняется в `Appointment.CalledAt`; сам вызов не меняет статус записи.

Медицинская история пациента состоит из завершенных приемов. Жалобы, осмотр, диагноз и назначения находятся в `Appointment`. Номер полиса и признак прикрепления входят в `Patient`, специальность хранится строкой у `Doctor`, номер кабинета есть в слоте и записи. Термин из Словаря не обязательно требует отдельного класса.

На диаграммах нет UI-классов. Состояния записи заданы перечислением `AppointmentStatus`: `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`, `NO_SHOW`. Неявку отмечает врач по ПРАВ14; автоматически она не фиксируется. Полный перечень методов смотрите в коде; на диаграмме классов оставлены основные.
